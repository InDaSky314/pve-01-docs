# BE9300 rebuild after the 2026-09-05 mesh meltdown

**Written the same night, while it was still fresh.** The owner meshed 5.1
(MT6000) with 9.1 (BE9300), then tried to add 7.1 (BE3600). Everything
collapsed, 9.1 became unreachable, and it had to be factory reset. This file
records what actually broke, what the GL.iNet web UI does that the CLI does
not, and the exact state the router was rebuilt into.

---

## 1. Do not mesh the PPPoE edge

The BE9300 is both the PPPoE head-end and the LAN gateway — the single device
everything depends on. GL mesh onboarding rewrites the participating devices'
bridge/LAN config, so restructuring the edge takes the admin path down with
everything else. With no Tailscale on the box there was no way back in, and a
factory reset became the only option.

**There was prior art.** `glinet-api-cli-runbook.md`, "Incident (2026-08-10):
3.1 unreachable via LAN — mesh backhaul to 9.1 dropped": the mesh link dropped
one-sided, `apcli0` stopped reassociating, never self-recovered, root cause
never identified, and *neither* Astromesh nor prplMesh was actually managing
it. GL meshing on this hardware is already documented as fragile and opaque.

**Rule: leave the edge un-meshed. Use wired backhaul / AP mode for coverage,
and confine any mesh to leaf devices that have their own independent admin
path.**

---

## 2. What the web UI does that `uci` + `ifup` does not

This is the core finding. Enabling a WireGuard client from the CLI *appears*
to work and then silently reverts: `network.wgclientN.disabled` flips back to
`'1'` on its own, with **nothing logged**. Four different CLI approaches
failed this way.

Diffing `uci export` before and after a single UI toggle showed why. The UI
does three things, and the CLI attempts only ever did the first:

1. `network.wgclientN.disabled='0'`
2. **Creates a firewall zone:**
   ```
   config zone 'wgclientN'
       option name 'wgclientN'
       option network 'wgclientN'
       option input 'DROP'
       option forward 'ACCEPT'
       option output 'ACCEPT'
       option masq '1'
       option masq6 '1'
       option mtu_fix '1'
       option enabled '1'
       option gl_vpn_rules '1'
   ```
3. **Creates the forwardings:**
   ```
   config forwarding 'lan2wgclientN'
       option src 'lan'
       option dest 'wgclientN'
       option gl_vpn_rules '1'
   config forwarding 'guest2wgclientN'   # same shape, src 'guest'
   ```

Without the zone and forwardings there is no NAT or forward path, so GL's own
service treats the instance as invalid and disables it again. The reversion is
a **missing precondition, not a bug** — and it is invisible, because nothing
warns you.

**`gl-session` does not exist on firmware 4.10.0** (`ash: gl-session: not
found`), despite `glinet-api-cli-runbook.md` documenting it. That runbook
section is stale for this box.

## 3. How route_policy encodes a client list

A tunnel rule scoped to specific devices carries exactly three extra options:

```
route_policy.@rule[N].from_type='ipset'
route_policy.@rule[N].from='src_mac<tunnel_id>'
route_policy.@rule[N].from_mac='AA:BB:..' 'CC:DD:..'      # uci list
```

Absent all three, the rule means **All Clients**. To scope a tunnel from the
CLI, set those and run `/usr/bin/rtp2.sh apply` — never
`/etc/init.d/network reload`.

```sh
uci set route_policy.@rule[2].from_type='ipset'
uci set route_policy.@rule[2].from='src_mac2939'
uci add_list route_policy.@rule[2].from_mac='BC:24:11:28:55:77'
uci commit route_policy && /usr/bin/rtp2.sh apply
```

This was verified live — it is how Tunnel 3 was scoped after the browser
extension dropped mid-session.

## 4. Why enabling a tunnel kept locking the owner out

Three fail-closed `ip rule` entries:

```
9910: not from all fwmark 0/0xf000 blackhole
9920: from all iif br-lan blackhole
```

Any LAN client without a routing mark is **blackholed, not sent to WAN**.
After the reset the MAC ipsets were empty, so nothing carried a mark and the
LAN had no internet at all. Routing *everything* through Zürich was the
owner's workaround to get back online — load-bearing, not cosmetic.

Combined with `killswitch='1'` on each tunnel rule, enabling a tunnel that
could not establish blackholed the whole LAN including the admin path.

**Mitigations applied:** `killswitch='0'` on all three rules, and the "Allow
Non-VPN Traffic" banner now confirms unmatched traffic uses standard internet.

## 5. The deadman rollback — use this before any risky router change

`/root/deadman.sh` on the BE9300, driven by cron every minute so it survives
SSH disconnect, tunnel loss and full lockout.

```sh
/root/deadman.sh arm 240 /etc/config/route_policy /etc/config/network /etc/config/firewall
# ... make the change, verify access ...
/root/deadman.sh cancel      # ONLY after access is confirmed
/root/deadman.sh status
```

If `cancel` is never reached, cron restores the snapshots, runs
`rtp2.sh apply` and reloads the firewall within 60 s of the deadline.

**A first version used a backgrounded `setsid` process and silently failed the
test** — it stayed armed and reverted nothing, because the process did not
survive the SSH session ending. Cron-driven is the version that works. Test
your rollback before trusting it.

## 8. Tailscale on the edge is not optional

Restore it **before** any other risky change. Without it, a lockout is a
factory reset.

- Enable with `uci set tailscale.settings.enabled='1'` — the init script gates
  on this and will silently do nothing otherwise.
- Its control traffic must egress **natively**, not through a tunnel, or a
  killswitch takes the out-of-band path down with everything else. Confirm
  with `ip route get <tailscale-derp-ip>` — it should show `dev pppoe-wan`.
- **Do not create a `network.tailscale` interface.** One was added during this
  rebuild and netifd cycled it up/down 94 times, which presented as Tailscale
  "flapping" and constant dnsmasq reloads. The system creates its own
  `firewall.tailscale0` zone; that is sufficient.
- A factory reset orphans the old tailnet node. The router re-registers with a
  `-1` suffix (`gl-be9300-1`) until the stale entry is deleted in the admin
  console.

## 9. The CLI recipe, validated end-to-end

Section 2's finding was proven by using it. Tunnel 2 was brought up entirely
from the shell, and `network.wgclient2.disabled` **stayed `0`** instead of
reverting — confirming the firewall zone and forwardings were the missing
precondition, not a guess:

```sh
# 1. zone
z=$(uci add firewall zone)
uci set firewall.$z.name='wgclient2';    uci set firewall.$z.network='wgclient2'
uci set firewall.$z.input='DROP';        uci set firewall.$z.forward='ACCEPT'
uci set firewall.$z.output='ACCEPT';     uci set firewall.$z.masq='1'
uci set firewall.$z.masq6='1';           uci set firewall.$z.mtu_fix='1'
uci set firewall.$z.enabled='1';         uci set firewall.$z.gl_vpn_rules='1'

# 2. forwardings -- note 'iot', which the web UI does NOT create
for s in lan guest iot; do
  f=$(uci add firewall forwarding)
  uci set firewall.$f.src="$s"; uci set firewall.$f.dest='wgclient2'
  uci set firewall.$f.gl_vpn_rules='1'
done

# 3. enable + apply
uci set network.wgclient2.disabled='0'
uci set route_policy.@rule[1].enabled='1'
uci commit; /etc/init.d/firewall reload; /usr/bin/rtp2.sh apply
```

**Trap:** enabling a rule without `from_type`/`from_mac` means *All Clients*,
and it will immediately hijack every unmatched device — pve-01 and CT107 were
pulled onto Frankfurt the moment rule[1] came up. Scope the rule in the same
change, or accept a window where everything rides the new tunnel.

A tunnel whose clients are bound by **subnet** rather than MAC still needs its
route_policy rule enabled (that is what instantiates the interface), so give it
a placeholder MAC that matches nothing and do the real binding with an
`ip rule`:

```sh
uci set route_policy.@rule[1].from_type='ipset'
uci set route_policy.@rule[1].from='src_mac6039'
uci add_list route_policy.@rule[1].from_mac='02:00:00:00:00:01'   # matches nothing
ip rule add from 192.168.91.0/24 lookup 1002 priority 5910        # the real binding
```

Persisted in `/etc/hotplug.d/iface/90-vpn-subnet-rules`, because `ip rule` is
runtime-only and does not survive a reboot.

## 11. OpenVPN is probably unnecessary

The full Surfshark **WireGuard peer catalogue survives on the box** —
`wireguard.peer_1500` is `United States - New York`, the exact endpoint the old
design used OpenVPN for. Since the only reason OpenVPN was needed is that one
tunnel cannot serve both a MAC list and an SSID, the cheaper fix is a **fourth
WireGuard tunnel instance** to peer_1500 for GIOT, rather than sourcing an
`.ovpn` profile and Surfshark *service* credentials. Recommended.

## 12. Meshing is a one-way door for remote access

**Meshing a GL node moves it onto 9.1's L2 segment and disables both SSH and
Tailscale on it.** This is the single most important operational fact learned
tonight, and it explains the whole incident: meshing the BE9300 as a *member* rather than
the head end removed its admin path outright, which is why a factory reset
became the only way back in.

Consequences:

- **9.1 (BE9300) is itself part of the mesh — as the head end.** It is not
  outside the mesh; being the *head end* is what preserves its SSH and
  Tailscale. Mesh *members* lose both. Everything else is reachable only
  through it, so the head end's admin path is the one that must never be
  given up.
- **Harvest anything you need off a node BEFORE meshing it.** Config, VPN
  profiles, credentials, keys. Afterwards there is no remote shell.
- A meshed node still answers on 9.1's LAN and keeps its **web UI on port 80**.
  The MT6000 post-mesh: `192.168.9.246`, ping OK, **80 open, 22 shut**. That
  web UI is the remaining management path.
- Its old addresses are dead: `192.168.5.1`, its WAN-side `192.168.1.12` and
  its tailnet address all stop answering. Do not read that as a dead device —
  check 9.1's DHCP leases for it by name first.

**Separately — an un-meshed GL router on 9.1's LAN also refuses SSH**, for a
different reason: from its point of view `192.168.9.x` is its *WAN*, and the
`wan` zone is `input DROP`. ARP shows `REACHABLE` while ICMP and ports 22/80 all
fail. The fix is either "SSH Remote Access" in its own UI, or reach it over
Tailscale before meshing.

## 13. Surfshark OpenVPN profiles — harvested 2026-09-06

Pulled off the Slate 7 (BE3600, `gl-be3600` over Tailscale) **before** meshing
it, and installed on 9.1 at `/etc/openvpn/profiles/`:

- 281 files under `profiles/94762/`, including
  `us-nyc.prod.surfshark.com_{tcp,udp}.ovpn` — the New York endpoint GIOT's
  design calls for.
- `profiles/94762/auth/username_password.txt` — the Surfshark **service**
  credentials (distinct from the account login), `chmod 600`.

Archive also kept at `/root/router-backups/slate7-openvpn-<stamp>.tgz`, 600.
**These are secrets: never commit them, never paste them.** Only the 9.1 copy
and that archive should exist.

This unblocks §11 either way — GIOT can now take a US OpenVPN tunnel *or* a
fourth WireGuard instance to `peer_1500`.

**The OpenVPN tunnel still needs the web UI, though.** The working shape was
read off the Slate 7, which runs one:

```
route_policy.@rule[N].via_type='openvpn'
route_policy.@rule[N].group_id='94762'                       # profile dir name
route_policy.@rule[N].tunnel_id='5039'
route_policy.@rule[N].profiles='/etc/vpn_profiles.d/profile5039'
route_policy.@rule[N].via='ovpnclient1'
```

and `/etc/vpn_profiles.d/profile5039` holds lines like `94762_85`, `94762_88` —
**indices into the profile group**. There is no manifest in
`/etc/openvpn/profiles/94762/` (only `auth/` and 280 `.ovpn` files), so the
index-to-filename mapping is internal to GL's `vpn-client.add_tunnel` handler
and cannot be reconstructed from disk. Create the tunnel in the UI; it can be
scoped and bound from the CLI afterwards using §9's recipe.

## 14. GIOT's US OpenVPN tunnel — how it was actually built

The blocker in §13 was that the profile *index* mapping is not on disk. It
turned out to live in **`/etc/config/ovpnclient`** — not `ovpn-client` or
`ovpn_client`, which is why earlier greps missed it. That file holds:

- an `@groups[N]` section: `group_id='94762'`, `group_name='SurfShark'`,
  `group_type='2'`, `auth_type='1'`, plus `username`/`password` (the Surfshark
  **service** credentials) and `work_mode='legacy'`;
- 280 `ovpnclient.94762_<client_id>` sections, each mapping a client_id to a
  `name`, a `path` under `/etc/openvpn/profiles/94762/`, `remote`, `cipher`
  and so on.

So the whole registry is UCI. It was transplanted wholesale from the Slate 7:

```sh
ssh slate7 'cat /etc/config/ovpnclient' | ssh glinet-9.1 'umask 077; cat > /etc/config/ovpnclient'
```

36 lines became 4799, and the UI immediately showed **SurfShark (OpenVPN) 280**
alongside the WireGuard set. New York is `94762_231` (TCP) / `94762_232` (UDP).

**Creating the tunnel in the UI, safely.** The Add New Tunnel wizard defaults
step 2 to *All Clients* — the same default that hijacked every unmatched device
when Tunnel 2 came up. It refuses to advance with zero devices selected
("Please select at least one device"), so use **Add Device** and enter a
placeholder MAC that matches nothing:

```
02:00:00:00:00:02
```

The tunnel is then created scoped to nothing, and the real binding is done with
a subnet `ip rule` as in §9. Verified: after creation, CT105 was still on
Zürich and pve-01 still native — no hijack.

Two UI quirks worth knowing: the profile search box does not filter the list
(neither display name nor filename), so locate an entry by scrolling or by
accessibility-tree reference; and "Selected Profile (0)" can read zero even
when a profile *is* selected — the wizard advances regardless.

## 16. Still outstanding

- **Tunnel 2 (Frankfurt)** down — no consumer until WALDO exists.
- ~~**guest/iot bridges down**~~ **RESOLVED.** Both were simply
  `network.<iface>.disabled='1'`. Setting them to `'0'` plus `ifup guest`/
  `ifup iot` instantiated `br-guest 192.168.90.1/24` and `br-iot
  192.168.91.1/24` with no disruption to `br-lan` or the tunnels. Open-Fields,
  GIOT and WALDO all confirmed broadcasting, and the WALDO subnet binding
  verified live: `ip route get 8.8.8.8 from 192.168.91.50 iif br-iot` returns
  `dev wgclient2 table 1002` (Frankfurt).

- **WALDO and GIOT SSIDs already exist** (`wireless.iot2g`/`iot5g` = WALDO,
  `wireless.guest2g/5g/6g` = GIOT). The problem is one layer down: the `iot`
  and `guest` interfaces are configured but **not instantiated** — no `br-iot`
  or `br-guest` device exists, so `ip route get ... iif br-iot` fails and
  nothing can broadcast. Bring those bridges up first; the SSIDs should follow.
- **US tunnel for GIOT** — see §11; prefer a fourth WireGuard instance to
  `peer_1500` (New York) over rebuilding OpenVPN. `/etc/openvpn/profiles` is
  empty after the reset and `ovpn-client` UCI is unset, so the OpenVPN route
  needs a Surfshark `.ovpn` plus their *service* credentials.
- **CT111 jellyfin-vod** powered off, so absent from the Zürich client list.
- **GIOT has no egress yet.** `br-guest` is up and broadcasting, but nothing
  binds it to a tunnel, and guest/iot fail *closed* — so GIOT clients are
  blackholed until the US tunnel (§11) exists. Expected, not a fault.

- **Meshing the MT6000 did not recover it** (tried 2026-09-05 ~23:40). After
  the mesh, `192.168.5.1`, `192.168.1.12` and its tailnet address all still
  fail to ping, and `big-gl` reads `offline, last seen 8h ago, tx 9984 rx 0` —
  still transmitting into a partner that no longer exists. A mesh cannot
  rescue a node that is not on the network; the count of unanswered transmits
  simply keeps climbing. **It needs a physical power cycle.** Importantly, the
  mesh attempt did *not* disturb the BE9300: LAN SSH, all three tunnels,
  br-lan/br-guest/br-iot and the full egress split were verified unchanged
  afterwards.

- **Slate 7 / BE3600 (7.1)** unreachable: no DHCP lease on 9.1, no ARP, and its
  tailnet node reads `offline, tx 312 rx 0` — the same stranded signature as
  the MT6000. Needs the same physical rescue before its OpenVPN profiles and
  credentials can be copied across.

- **MT6000 (5.1)** down: ARP `FAILED` on the UDR's `br0`, Tailscale shows
  `tx … rx 0`. Stranded hunting a mesh partner that no longer exists. Needs a
  physical power cycle; no software path reaches it.
