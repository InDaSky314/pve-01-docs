### Claude Code's review of AGY's design (2026-09-03)

The design is sound and I endorse the core of it: SQLite **FTS5** over the existing XMLTV
(verified available, 3.46.1, on both host and CT 105), cluster-by-(title, rounded start,
rounded duration) for multi-channel dedup, booking through the arbitration gateway, and a
hard cap rather than uncapped extension. Its rejected-alternatives list is right, especially
refusing direct writes to `mct-bookings.json`.

**One flaw that would break it as drawn.** The design places `epg.db` at
`/srv/media-core/epg/epg.db` and has `dvr-dashboard` query it. But `dvr-dashboard` runs on
the **host**, and the host's `/srv/media-core/` contains only `sync` and `wholphin` — `epg/`
exists only inside CT 105. The dashboard cannot open that SQLite file. It already works
around this everywhere else by falling back to `pct exec 105 -- cat` (see its `pct()` helper,
used for `xepg.json`), and AGY's own benchmark measured the `pct exec` penalty at ~2.0s — then
designed as if the file were local anyway.

*Fix:* run the indexer **on the host**, pulling `epg.xml` through the existing `pct()` helper
on rebuild only, and write `epg.db` somewhere host-visible — `/var/lib/dvr-dashboard/epg.db`,
next to the other dashboard state. Rebuilds are rare (daily sync + hourly PPV), so paying ~2s
there is fine, and every query then runs locally at full speed with no CT 105 dependency.
Drive it from a host timer that compares `pct exec 105 -- stat -c %Y` against the stored mtime,
rather than checking per query.

**Second gap:** `epg-find --book` calls the dashboard API, which requires HTTP Basic auth from
`/etc/dvr-dashboard.auth`. The design never mentions credentials. The CLI runs as root so it
can read that file, but it must be specified — and must never echo it.

**Judgement call, not a defect:** a +60m default pad for untracked live sport is a lot of a
one-connection tuner to hold. It is clamped so it cannot destroy a following recording, but it
will block back-to-back bookings. Prefer an explicit per-booking pad over a large silent default.

**Correction to my own figure:** the EPG holds **38,189 programmes**, not the 24,503 I reported
earlier — `grep -c` counts matching *lines*, and this XML packs many programmes per line.
AGY's ~38,200 was right. Channel count 1,224–1,225 either way.

Non-negotiables for the review:

* booking must go through the dashboard's existing `_record_game` arbitration — **never** write
  `mct-bookings.json` directly, or the single tuner can be double-booked
* the same fixture appears on multiple channels (Premier League on both Chicago NBC 5 and Green
  Bay NBC 26); group results so the channel is chosen deliberately
* arbitrary programming has **no** auto-extend signal — EPG `stop` is a plan, not an outcome

## 3. Saturday's OpenLigaDB latency measurement

`oldb-latency-probe.timer` fires **2026-09-05 19:00 CEST** for Schalke v Bayern (matchID 83172,
kickoff 18:30). It records when `matchIsFinished` actually flips, so MCT can eventually stop a

`/var/lib/dvr-dashboard/oldb-latency-83172.jsonl`. See
[mct-bundesliga-stop-signal.md](mct-bundesliga-stop-signal.md).

**in-progress recording**, not the live channel: a second tuner request on a one-connection
account will fail and may disturb the recording.
