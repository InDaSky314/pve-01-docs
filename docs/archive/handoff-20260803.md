## The hypothesis — artwork is bound to the OLD channel numbers

Not a hunch. The donor channels are exactly the previous occupants of those
numbers:

| now at | channel | shows the icon of | which used to be at |
|---|---|---|---|
| 214 | ANTENNA TV | BBC WORLD NEWS | **214** |
| 210 | AMC HD | BLOOMBERG HD | **210** |
| 206 | AWE | NEWSMAX HD | **206** |
| 215 | ASPIRE | AL JAZEERA ENGLISH | **215** |
| 216 | AWE HD | EURONEWS | **216** |
| 217 | AXS TV | 7NEWS BOSTON | **217** |
| 218 | AXS TV NOW | BOSTON 25 NEWS | **218** |
| 219 | BBC AMERICA | CHEDDAR | **219** |
| 201 | LATIN PASIONES | MSNBC HD | **201** |

Every donor is a member of the pre-renumber US News block (200-249). The
receivers are the channels that now occupy those numbers.

The reciprocal case confirms it: **channel 300 LIFETIME MOVIE NETWORK is
serving LAFF TV's correct 9,697-byte logo**, and LAFF TV now sits at 200 with
the wrong one. The art did not vanish; it stayed with the number.

### Test before fixing

Reconstruct the pre-renumber numbering from
`/srv/media-core/sync/config.json.bak-renumber-commit1` (on CT 105) or the
NextPVR backup `npvr.db3.bak-prescan2` (on CT 112), then for each of the 30
check: **does the donor's OLD number equal the receiver's CURRENT number?**

If that holds for ~30/30, the hypothesis is confirmed and the mechanism is
number-keyed artwork somewhere in the chain. If it holds for only some, stop
and re-diagnose.

### Where the number-keying could live

Candidates, in order of likelihood — do not assume, check:

1. **Jellyfin's own image cache path.** Channel images live under
   `metadata/livetv/<item-guid>/`. If a guid is derived from channel number
   rather than identity, a renumber silently reassigns artwork.
2. **NextPVR's `media/channels/` filenames.** These are name-keyed, so this
   should be immune — but 30 channels disagree, so verify rather than assume.
3. **The icon host.** Filenames are name-keyed too. Confirm what
   `/icons/<name>.png` returns for the 30 receivers.

Note the layer count: the artwork chain is **four** layers, not the three the
icons runbook currently documents — archive -> icon host -> NextPVR files ->
Jellyfin rows. Missing the icon host is why an earlier "fixed" claim failed.

## How the icon corruption happened — do not repeat

`icon-archive export` was run **while production's channel images were
misaligned**. It captured wrong logos (CNN's under LAFF TV's name), the icon
host served them, CT 112 re-imported from the icon host, and the corruption
was laundered into the source of truth. Later checks validated against that
same corrupted source and passed.

Two tooling fixes are already in place:
- `extract` uses **strict source precedence** (NextPVR files > generated >
  Jellyfin cache), not largest-file-wins
- `US: CNN 4K` and `CNN 4K` are grouped as one channel, so the same channel
  cannot hold two different images

Recovery was only possible because blobs are content-addressed and
`manifest.pre-ct112.json` predates the contamination. **Snapshot before any
change, and never archive while a known-bad state exists.**
