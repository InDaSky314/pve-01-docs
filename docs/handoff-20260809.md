## Work stream 1: stalled-recording watchdog + auto-restore/stitch

Triggered by an Aug 8/9 Twins @ Brewers recording silently truncating to ~2 hours of
a 3+ hour game — the file just stopped growing, zero error logged anywhere, upstream
IPTV stream apparently died mid-stream.

- **Detection**: `check_stalled_recordings()` compares real on-disk file size across
  10-minute ticks (via `timers.json` on CT105, not the public REST API, which doesn't
  expose `RecordingPath`). Flags a stall if growth is under 2MB across an 8+ minute
  gap with 15+ minutes still scheduled. Independent review (agy) caught 3 real bugs
  before this shipped: `checked_at` being overwritten even on a skipped tick,
  transient timers-fetch failures wiping all stall state, and `alerted_at` never
  clearing on recovery. All fixed.
- **Auto-restore**: cancels the stalled timer, creates a continuation timer for the
  same channel through the original scheduled end. First build didn't actually cancel
  the original (would have left two timers fighting for this household's
  single-stream IPTV plan) — caught in review, fixed, and the cancel-then-recreate
  sequence was proven for real against a live throwaway timer (`DELETE` → 204,
  original dropped from active timers, new one reached `InProgress`) before deploy.
- **Stitch**: once the restore timer completes, concatenates original + restore via
  `jellyfin-ffmpeg`'s concat demuxer inside CT105's `jellyfin` container, writes
  alongside the originals (never deletes them), discloses the real content gap in the
  completion email.
- Full build/review trail: `/root/agy-reports/sports-dvr-auto-restore-stitch`,
  `test_auto_restore_stitch.py`, and the timestamped reports in that directory.

## Work stream 2: DVR Schedule / Recordings bug hunt

Started from a real report (in-progress recording playback still not working from the
Recordings library) and expanded into five real, independent bugs, all found and
fixed by testing directly against the household's own live data on the real
Chromecast rather than synthetic test cases. Full technical writeup in
`livetv-custom-build-and-updates-20260726.md` §18 — summary here:

1. Recordings library browse hung 26–45+ seconds (Jellyfin's `EnableUserData=true`
   default triggers an expensive recursive calculation specifically for the
   `CollectionType == null` Recordings folder against the household's 550k+ item
   database). Fixed client-side, scoped narrowly so normal libraries keep their
   watched/favorite indicators.
2. DVR Schedule crashed the whole screen for every timer whenever any single ad-hoc
   timer (which is *all* of them — both `sports-dvr-auto` and the dashboard's own
   Record button schedule by channel+time, never by EPG program) lacked linked
   `ProgramInfo`. Fixed with a null-safe fallback.
3. Cancel Recording was missing on those same ad-hoc timers (dialog couldn't tell
   they were already scheduled) — fixed.
4. Cancel Recording / Watch buttons were also hidden on any recording that overran
   its originally-scheduled end time — caught live against a real recording (Weather
   AM, which turned out to run ~2 hours past its 1-hour scheduled window before
   stopping on its own — worth a separate look, see Open) — fixed.
5. Clicking a Recording directly in the library showed literal "Unsupported item
   type: Recording" — the router never had a case for it. Fixed, verified by
   actually deleting a real test recording through the fixed path (file + library
   entry both confirmed gone).
6. "Watch recording in progress" from DVR Schedule's Active Recordings list did
   nothing — it was redundantly re-querying `/LiveTv/Recordings` filtered by channel
   for an item it already had in hand, and that filtered query doesn't reliably
   return a genuinely `InProgress` recording. Simplified to navigate directly.

## Standing facts worth keeping

- **Recording an in-progress program's live tap is unsafe on this stack** — this is
  *why* "Watch recording in progress" exists as a distinct path at all (see
  `ProgramDialog.kt`'s own comment): tapping a channel that's mid-recording can start
  mid-stream with no valid H.264 headers on some backends. Always prefer the
  recording-file path when both are available.
- **Timers and Recordings are separate concepts** in Jellyfin's model, confirmed
  repeatedly this session — a `Status: InProgress` Timer does not guarantee
  `/LiveTv/Recordings` (filtered or not) returns anything for it. Don't build new
  logic that assumes otherwise; query the Timer directly when that's what's actually
  needed.
